Industrial Data Protocol Guide
Understanding OPC-DA
vs OPC-UA
OPC stands for Open Platform Communications — the standard way industrial systems (like BHEL's DCS) expose sensor data to other software. Think of it as the USB standard for factories. There are two generations: the old one (DA) and the modern one (UA). You need to understand both because your client may be using either.
BORN IN 1996
OPC-DA
DATA ACCESS — THE OLD STANDARD
Built on Microsoft's COM/DCOM technology. Think of COM like a very old Windows-only plugin system. OPC-DA was the first standard that let SCADA software read sensor values from DCS systems. It works — but it's tied completely to Windows and has serious network limitations.
Windows Only COM/DCOM LAN Friendly Firewall Problems No Security Legacy
BORN IN 2008
OPC-UA
UNIFIED ARCHITECTURE — THE MODERN STANDARD
A complete rewrite. No more Windows dependency. Runs on Linux, Raspberry Pi, embedded systems — anything. Uses standard TCP sockets instead of COM. Has built-in security (TLS encryption + certificates). Has subscriptions — meaning the server pushes data to you instead of you polling. The industry is moving entirely to UA.
Cross-Platform TCP/IP Built-in Security Subscriptions Firewall Friendly Python Native
SIMPLE ANALOGY
OPC-DA is like a fax machine
It works. People used it for 30 years. But it only works in one building (Windows), needs special phone lines (DCOM ports), and has no security. Everyone is slowly replacing their fax machines.
SIMPLE ANALOGY
OPC-UA is like WhatsApp
Works on any device, any OS. End-to-end encrypted. You can subscribe to a group and get messages pushed to you automatically. Works through firewalls. That's the UA model — modern, secure, push-based.
OPC-DA Detailed Flow
How OPC-DA Actually Works
OPC-DA uses Microsoft's COM/DCOM (Distributed Component Object Model). Your software calls a Windows component which talks to the DCS. Imagine it as a chain of Windows DLL calls across the network.
OPC-DA Complete Data Flow WINDOWS ONLY
STEP BY STEP
1
DCS System Has OPC-DA Server
The plant's DCS (ABB, Siemens, Honeywell) has an OPC-DA server installed on a Windows machine. This server exposes all sensor values as "tags" — addressable items like "Plant.Turbine.Bearing1.Temperature"
2
Your OPC Client Calls via DCOM
Your client code (also on Windows) makes a DCOM call — like a remote function call — to connect to the OPC server. Windows handles the network transport using random high-numbered ports (135 + random). This is why firewalls hate OPC-DA.
3
Client Reads Tags by Polling
Your code says "give me the value of tag T001, T002, T003..." every N seconds. The server responds with current values. This is synchronous polling — you ask, it answers. There is no push mechanism.
4
You Parse and Forward
Your OPC client code reads the values and converts them into your internal format, then sends to Redis.
THE PROBLEMS
🔥 Windows Only
COM/DCOM is a Windows technology. Your OPC client machine MUST be Windows. You cannot run this on Linux, Docker, or a Mac. This locks your Machine 1 to Windows Server.
🔥 Firewall Nightmare
DCOM uses port 135 to negotiate, then picks a RANDOM high port (1024–65535) for actual data. You cannot predict which port to open. Either disable the firewall or install special DCOM tunnel software.
🔥 No Security
No encryption. No certificates. Authentication is Windows user accounts only. Not suitable for anything beyond a tightly controlled local network.
🔥 Polling Only
You must poll at a fixed interval. All 500 sensors polled every 10 seconds whether they changed or not. Wasteful and you can't do per-sensor frequencies natively.

OPC-UA Detailed Flow
How OPC-UA Actually Works
OPC-UA uses plain TCP sockets on a fixed port (default 4840). Think of it as a very structured API over TCP — no Windows dependency, no random ports, encrypted by default.
OPC-UA Complete Data Flow CROSS-PLATFORM · PORT 4840
STEP BY STEP
1
Connect to OPC-UA Server
Your Python code connects to opc.tcp://server-ip:4840. One fixed port. Works through firewalls. The server could be on the DCS machine, a separate gateway, or your simulator. TLS handshake happens here — certificates are exchanged.
2
Browse the Address Space
The server exposes an "address space" — a tree of nodes. You can browse it like a folder structure: Root → Objects → Plant → Turbine → Bearing1 → Temperature. Each node has a NodeId — a unique identifier you use to reference it.
3
Create a Subscription
Instead of polling, you create a Subscription and add MonitoredItems to it. Each MonitoredItem is one sensor node. You tell the server: "tell me when this value changes" or "tell me every 10 seconds". The server does the work — you wait for pushes.
4
Server Pushes Data to You
When a sensor value changes beyond the configured deadband, or when the interval fires — the OPC-UA server sends a Publish notification to your client. Your DataChangeHandler fires with the new value. You publish to Redis immediately.
5
Per-Sensor Configuration
T001 bearing temp can have a 10s interval + 0.5°C deadband. B012 steam pressure can have 5s interval + 0.1bar deadband. G005 frequency can have 2s interval + 0.01Hz deadband. Each sensor is independently configured.
THE ADVANTAGES
✓ Cross-Platform
Python library asyncua runs on Linux, Windows, Mac. Your Machine 1 can be any OS. Docker-friendly. No Windows Server licence needed.
✓ Single Fixed Port
Always port 4840 (or 4843 for encrypted). One firewall rule. No random ports. IT teams at plants love this.
✓ Push-Based Subscriptions
Server pushes when values change. Per-sensor intervals AND deadbands. A stable temperature at 85°C generates zero network traffic until it actually moves.
✓ Built-in Security
TLS encryption, X.509 certificates, user authentication. Suitable for industrial cybersecurity requirements which are increasingly mandated at PSU plants.
✓ Information Modelling
Sensors aren't just values — they have metadata: engineering units, ranges, descriptions, alarm limits. All browsable from the address space. Self-describing data.

OPC-UA Deep Dive
Subscriptions — The Key Concept
This is what makes OPC-UA fundamentally better for your architecture. Understanding this will let you answer BHEL's technical questions confidently.
📋
Subscription
A container you create on the OPC-UA server. Like signing up for a mailing list. One subscription can monitor hundreds of sensors. Has a publishing interval — the minimum frequency for notifications.
🎯
MonitoredItem
Each sensor you add to a subscription becomes a MonitoredItem. It has its own sampling interval (how often the server checks it) and deadband (minimum change to trigger a notification). You can have 500 MonitoredItems in one subscription.
📡
Deadband
A noise filter. If you set deadband=0.5°C, the server only notifies you when the temperature changes by more than 0.5°C. A sensor sitting at 85.3°C fluctuating ±0.1°C generates zero traffic. Critical for reducing noise.
OPC-DA Polling — What actually happens
Every 10 seconds, your code wakes up and asks for all 500 sensor values. Whether they changed or not. Wastes network and CPU.
t=0s
Poll: read all 500 sensors. T001=85.2, T002=91.0... → send all 500 to Redis
t=10s
Poll again: T001=85.3 (barely changed), others same. → send all 500 again
t=20s
Poll again: everything same. → send 500 unchanged values
t=25s
T003 starts overheating but poll interval hasn't fired yet. You won't know for 5 more seconds.
t=30s
Poll: finally see T003 is critical. 5 second delay in detection.
OPC-UA Subscriptions — What actually happens
Server monitors sensors continuously. Notifies your client only when something changes or interval fires. Zero polling overhead.
t=0s
Connected. Subscription created. 500 MonitoredItems registered. Server starts monitoring internally.
t=1s
T003 value unchanged, T001 changed by 0.3°C (below deadband). → nothing sent. Zero traffic.
t=10s
Interval fires for stable sensors. Small batch notification. → only changed values sent.
t=25s
T003 crosses deadband. Server pushes IMMEDIATELY — does not wait for next interval. Alert detected at t=25s, not t=30s.
t=30s
Interval fires. Other sensors report their periodic updates.

# Machine 1 — OPC-UA Server wrapping your Python Simulator
# asyncua library: pip install asyncua
# This exposes your simulator data as real OPC-UA nodes
# In production: replace simulator with DCS feed

from asyncua import Server
from asyncua.common.node import Node
import asyncio

class OPCUAServerWrapper:
    def __init__(self, simulator):
        self.simulator = simulator
        self.server = Server()
        self.sensor_nodes = {}   # sensor_id → OPC node

    async def setup(self):
        # Start OPC-UA server on port 4840
        await self.server.init()
        self.server.set_endpoint("opc.tcp://0.0.0.0:4840")
        self.server.set_server_name("BHEL Plant Simulator")

        # Create namespace
        ns = await self.server.register_namespace("BHEL_PLANT")

        # Create folder structure: Root → Plant → Turbine → T001
        plant = await self.server.nodes.objects.add_folder(ns, "Plant")

        for subsystem in ["Turbine", "Boiler", "Generator", "Cooling"]:
            folder = await plant.add_folder(ns, subsystem)

            # Add each sensor as a variable node
            for sensor in self.simulator.get_sensors_by_subsystem(subsystem):
                node = await folder.add_variable(
                    ns, sensor.id, sensor.baseline_value
                )
                # Set engineering unit metadata — self-describing!
                await node.set_writable()
                self.sensor_nodes[sensor.id] = node

    async def update_loop(self):
        # Every tick: push simulator values into OPC nodes
        async with self.server:
            while True:
                readings = self.simulator.tick()
                for reading in readings:
                    node = self.sensor_nodes[reading.sensor_id]
                    await node.write_value(reading.value)
                await asyncio.sleep(1)  # update every second

class OPCUAClient:
    def __init__(self, data_change_handler):
        self.handler = data_change_handler
        self.client = Client(url=OPC_SERVER_URL)

    async def connect_and_subscribe(self):
        async with self.client:
            # Browse address space to find all sensor nodes
            sensor_nodes = await self._discover_sensors()
            print(f"Found {len(sensor_nodes)} sensor nodes")

            # Create ONE subscription for all sensors
            subscription = await self.client.create_subscription(
                period=1000,   # server checks every 1s
                handler=self.handler
            )

            # Add each sensor as a MonitoredItem
            # Each sensor can have DIFFERENT sampling interval
            for node_id, config in sensor_nodes.items():
                await subscription.subscribe_data_change(
                    nodes=config["node"],
                    sampling_interval=config["interval_ms"],
                )

            # Keep alive — server will push data to our handler
            await asyncio.sleep(float("inf"))

    async def _discover_sensors(self):
        # Browse: Root → Objects → Plant → [subsystems] → sensors
        plant = await self.client.nodes.root.get_child(
            ["0:Objects", "2:Plant"]
        )
        sensors = {}
        for subsystem_node in await plant.get_children():
            for sensor_node in await subsystem_node.get_children():
                name = (await sensor_node.read_browse_name()).Name
                sensors[name] = {
                    "node": sensor_node,
                    "interval_ms": get_sensor_interval(name)
                }
        return sensors

def get_sensor_interval(sensor_id: str) -> int:
    # Per-sensor sampling intervals (milliseconds)
    if sensor_id.startswith("G"):  return 2000   # Generator: 2s
    if sensor_id.startswith("B"):  return 5000   # Boiler: 5s
    if sensor_id.startswith("T"):  return 10000  # Turbine: 10s
    return 15000                                  # Default: 15s
# The DataChangeHandler — fires every time a sensor value changes
# This is the heart of the OPC-UA subscription pattern

from asyncua import ua
import json, asyncio
from datetime import datetime, timezone

class DataChangeHandler:
    """
    OPC-UA calls datachange_notification() automatically
    whenever a MonitoredItem's value changes beyond deadband
    OR when the sampling interval fires.
    No polling. No loops. Pure event-driven.
    """

    def __init__(self, redis_client, sensor_registry):
        self.redis = redis_client
        self.registry = sensor_registry  # id → metadata

    async def datachange_notification(self, node, val, data):
        # This fires AUTOMATICALLY when OPC-UA server pushes
        sensor_id = await node.read_browse_name()
        sensor_id = sensor_id.Name  # e.g. "T003"

        meta = self.registry.get(sensor_id)
        if not meta:
            return

        # Compute status against thresholds
        pct = val / meta["max_threshold"]
        status = "critical" if pct >= 1.0 else \
                 "warning"  if pct >= 0.8 else "normal"

        reading = {
            "id":            sensor_id,
            "name":          meta["name"],
            "subsystem":     meta["subsystem"],
            "value":         round(val, 3),
            "unit":          meta["unit"],
            "status":        status,
            "max_threshold": meta["max_threshold"],
            "timestamp":     datetime.now(timezone.utc).isoformat()
        }

        # Publish to Redis channel — FastAPI WebSocket picks it up
        channel = f"subsystem:{meta['subsystem']}"
        await self.redis.publish(channel, json.dumps(reading))

        # Also update rolling buffer for new client catchup
        key = f"sensor:{sensor_id}"
        score = datetime.now().timestamp()
        await self.redis.zadd(key, {json.dumps(reading): score})
        await self.redis.zremrangebyscore(key, 0, score - 600)  # keep 10min
# Full wiring — how everything connects on Machine 1
# Run this single service: python opc_bridge.py

import asyncio
import aioredis
from simulator import SimulatorService, SensorRegistry
from opc_server import OPCUAServerWrapper
from opc_client import OPCUAClient
from handlers  import DataChangeHandler

async def main():
    # 1. Connect to Redis on Machine 2
    redis = await aioredis.create_redis_pool(
        "redis://machine2-ip:6379"
    )

    # 2. Start Python simulator (demo mode)
    #    In production: skip this, point to real DCS
    registry = SensorRegistry()
    simulator = SimulatorService(registry)

    # 3. Wrap simulator in OPC-UA server
    opc_server = OPCUAServerWrapper(simulator)
    await opc_server.setup()

    # 4. Create DataChangeHandler (fires on every sensor update)
    handler = DataChangeHandler(redis, registry.as_dict())

    # 5. OPC-UA client subscribes to the server
    opc_client = OPCUAClient(data_change_handler=handler)

    # 6. Run everything concurrently
    await asyncio.gather(
        simulator.run(),         # generates data
        opc_server.update_loop(), # pushes to OPC nodes
        opc_client.connect_and_subscribe(),  # subscribes + forwards to Redis
    )

asyncio.run(main())

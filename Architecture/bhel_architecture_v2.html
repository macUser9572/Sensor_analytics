Section 05 — New Component
Sensor Failure Handling — 4 Layers
The "silent failure" problem: a dead sensor and a stable sensor both produce silence. All 4 layers work together to detect and surface every failure mode.
1
OPC-UA Quality Codes — Hardware failures
Every OPC-UA reading carries a StatusCode. When a sensor physically fails, cable breaks, or field device times out — the DCS marks that tag as Bad quality and pushes a notification immediately. No polling wait.
# StatusCode values from OPC-UA server: Good → normal processing Bad_NodeIdUnknown → sensor disconnected Bad_Timeout → field device not responding Bad_OutOfService → sensor marked offline Uncertain_LastUsableValue → questionable, flag it
2
OPC-UA MaxKeepAlive — Stable sensor silence
Subscription config: max_keepalive_count=3 at 10s publishing interval = server MUST send a keepalive notification every 30 seconds even if no value changed. Stable sensor at 85°C still produces a heartbeat every 30s. If keepalive stops → sensor is gone.
# Subscription config on OPC-UA client: subscription = await client.create_subscription( period=10000, # 10s publishing interval max_keepalive_count=3, # keepalive every 30s max handler=handler )
3
Application Watchdog Timer — Network/OPC failures
Runs in FastAPI on Machine 2. Tracks last_seen timestamp per sensor. If no notification (value change OR keepalive) for 45 seconds → fires SENSOR_MISSING alert. Also detects recovery — when data resumes, fires SENSOR_RECOVERED alert.
# Watchdog checks every 15 seconds: if (now - last_seen[sensor_id]) > 45: fire_alert("SENSOR_MISSING", sensor_id) # On next notification arrival: if sensor_id in fault_sensors: fire_alert("SENSOR_RECOVERED", sensor_id)
4
UI Staleness Indicators — Operator visibility
Both React and Flutter show data freshness state on every sensor. Four distinct visual states ensure operators always know exactly what they're looking at.
● LIVE → Green · updated within 2× expected interval ⚠ STALE → Amber · last update > 2× expected interval ~ UNCERTAIN → Yellow · OPC quality = Uncertain ✕ FAULT → Red · SENSOR_MISSING or SENSOR_FAULT alert
Section 06 — Updated
Alert System — 6 Types
Expanded from 2 to 6 alert types. All go through the same Redis alerts channel → WebSocket → both React and Flutter.
TYPE 01
⚠ Warning Threshold
Value reaches 80% of max_threshold. Sensor still functioning. Early warning for operators.
SOURCE: Alert Engine (in-memory) · EXISTING
TYPE 02
🔴 Critical Threshold
Value reaches 100% of max_threshold. Immediate attention required. Deduplication — one alert per event.
SOURCE: Alert Engine (in-memory) · EXISTING
TYPE 03
✕ Sensor Fault
OPC-UA StatusCode = Bad. Sensor physically failed, cable broken, or field device not responding. Fired immediately on OPC notification.
SOURCE: OPC DataChangeHandler · NEW
TYPE 04
~ Sensor Uncertain
OPC-UA StatusCode = Uncertain. Data is questionable but last known value provided. Show in UI with uncertainty flag.
SOURCE: OPC DataChangeHandler · NEW
TYPE 05
⏱ Sensor Missing
No notification (value or keepalive) received for 45 seconds. Covers network failures and OPC-UA server crashes that produce no Bad quality code.
SOURCE: Watchdog Timer · NEW
TYPE 06
✓ Sensor Recovered
Data resumes after a FAULT or MISSING state. Fired when Watchdog sees first notification from a previously faulted sensor. Info severity.
SOURCE: Watchdog Timer · NEW
Section 07 — New Feature
Multi-Sensor Comparison
Available on both React and Flutter. Cross-subsystem selection. Single overlay chart. New backend endpoint required.
🖥️ React Dashboard — Compare Flow
1
Sensor List Section (sidebar)
Dedicated section in React sidebar. Lists all sensors grouped by subsystem. Each row has a checkbox. User can select across subsystems freely.
2
Compare Button in Header
Persistent in top header. Shows count: "COMPARE (3) · 2 subsystems". Activates when ≥2 sensors selected. Clear All option.
3
Compare Chart View
Replaces main content area. Plotly line chart, one trace per sensor, color-coded. Dual Y-axis if units differ. Time range selector: 15min / 1hr / 6hr.
4
Data Source
Calls GET /data/sensors/compare?ids=T001,T003,B012&minutes=60. TimescaleDB returns time-aligned readings for all selected sensors.
📱 Flutter App — Compare Flow
1
Sensor List with Checkboxes
Each subsystem screen shows all sensors with checkboxes. User selects T001, T003 from Turbine screen.
2
Go Back — Select from Another Subsystem
User taps back to home. Goes to Boiler. Selects B012. Selection persists across navigation. AppBar shows: "COMPARE (3) · 2 subsystems".
3
Tap COMPARE in AppBar
Navigates to Compare Chart Screen. fl_chart LineChart with multiple traces. Dual Y-axis if units differ (°C left, bar right).
4
Clear and Start Over
"Clear All" button on compare screen resets selection. User can start a new comparison without going back through all subsystems.
NEW BACKEND ENDPOINT REQUIRED
GET /data/sensors/compare?ids=T001,T003,B012&minutes=60 -- TimescaleDB query (time-aligned, all sensors together): SELECT time_bucket('15 seconds', time) as bucket, sensor_id, avg(value) as value FROM readings WHERE sensor_id = ANY('{T001,T003,B012}') AND time > NOW() - INTERVAL '60 minutes' GROUP BY bucket, sensor_id ORDER BY bucket ASC -- Response: time-aligned array, one row per sensor per bucket -- Frontend plots each sensor_id as a separate trace
